# SoulComputerUse 测试约定

## 锁用例的三条硬规矩

`soulcomputeruse` 的单实例锁是**全机唯一**的，测试如果直接拿它，就会和执行中的真实会话、以及别处的测试互相干扰。所以：

1. **锁用例一律用运行期唯一锁名**，绝不用生产名。测试走 `SingleInstanceLock.Acquire(name)` / `IsHeldByAnyone(name)`（`internal` + `InternalsVisibleTo` 只对测试程序集开放），每次用例各自生成一个 `Global\SoulComputerUse-Test-<guid>`；生产入口 `Acquire()` 永远只引契约钉死的那个名字，并由一条**纯字符串断言**守住它。
2. **跨进程用例 kill 后必须等进程真退出**，再断言结果。只发 kill 不等待，下一个用例会在「上一个 holder 还没死」的窗口里跑，表现出来就是「锁被占」。
3. **跑完不许有本用例留下的 holder 存活**。用锁名探测本用例的对象是否已消失，即可证明自己没有泄漏；不要按进程名扫描，那会误伤别的测试类正在使用的 helper。

## 跑法

推荐**先构建、再以 `--no-build` 跑测试**：

```bash
dotnet build SoulComputerUse.slnx
dotnet test SoulComputerUse.slnx --no-build
```

原因是一个已经观察到的现象：直接 `dotnet test SoulComputerUse.slnx` 时，解决方案里的两个测试工程会一起构建并启动，偶发出现**整个集成工程一次全红、总耗时只有百毫秒量级**的形态。那不是断言失败（断言失败不会整工程在同一瞬间全红），而是**测试宿主在装配加载阶段就中止了**。把构建和测试分成两步、测试阶段不再构建，可以消掉这类启动期竞态。

## 红了怎么办：先分形状，再决定要不要重跑

**「重跑一下就好」是埋 bug 的最快方式。** 判红固定按下面三步走：

1. **先看有没有用例名和断言文本**，再看总耗时。
2. **有名字 = 断言级，必须查到底**，不得以重跑掩盖。断言级不稳定与构建/启动无关，`--no-build` 无法消除它。
3. **连用例名都没有、耗时又极短**，才按**宿主中止**处理：按上面的 `build` + `--no-build` 重跑，并且**只记录一次**；重跑不掉的，就不是噪声，回到第 2 步去查。

形状示例（都是本仓库真实出现过的）：

- **无名 + 整个测试工程一次全红 + 总耗时百毫秒量级**（见过 63 条 108ms、也见过 90 条 70ms）＝ 宿主级中止。重跑前**先看输出里有没有「程序集初始化方法 … 引发异常」这一行**，因为同一种形态至少有两个来源：一是测试宿主在装配加载阶段中止，二是**运行前预检主动拒绝启动**（机器上残留了其他运行留下的 holder 进程）。后者实际上**是有名字的**：输出中会写明「refuses to start on a dirty machine」和进程 id。出现该行即表示机器状态不干净，**不是**偶发的启动失败，必须查明是哪个用例未清理进程，不得以重跑掩盖。
- **有名 + 单条失败 + 有断言文本**（例如一条并发用例报出「应为 1、实际 0，退出码里有 -1」）＝ 断言级，其背后是一次真实的进程误杀，必须修复，重跑只会破坏证据。

结论：**整工程同时全红不等于「不是真问题」**，只等于「这一轮没跑到用例」——先分清是宿主中止还是预检拦下，再决定下一步。

## 结论不能只看程序状态码

**凡是被观察对象出现在用户屏幕上的实验，结论必须包含「用户观察到了什么」。** 程序能证明的只有它自己那条通道的状态（连没连上、状态码几），**不能代替用户作证**。

本仓库的真实教训：一次 RDP 连接实验里，程序状态从 2 走到 1（连接中 → 已连上），据此写下「没弹凭据框、直接进桌面」；用户说明「那是我自己登录输入的密码」后结论即被推翻——登录界面确实出现过，只是程序无法观测。**正确做法是在实验中直接询问用户观察到什么，然后将「用户观察到 A / B / C」与「程序读取到什么」并列记录，两者不一致时以用户观察到的内容为准。**



## 并行

- **集成测试程序集关掉方法级并行**（`[assembly: DoNotParallelize]`）：它碰的是真实内核对象与真实机器策略值，全跑只要几秒，确定性比几毫秒值钱。
- **契约测试程序集可以并行**：它只做纯决策、字符串核对与源码扫描，不碰锁也不写机器状态。

## 「名字说要验真机，实际跑在虚拟化环境」是更坏的假绿

一条用例的名字写着「at the machine DPI」「按真实分辨率」「真机尺寸」，实际却跑在被虚拟化的环境里，它证明的**不是产品行为，而是它自己的假设**。这比没测更坏，因为看起来是绿的。

规矩：

1. **带「机器 DPI / 真机 / 真实分辨率」这类字眼的用例，必须先自证环境**：进程必须是 Per-Monitor V2（`SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)` 之后用读回接口确认），不达标就**当场让整套失败**，宁可红也不许悄悄跑在默认 DPI 上。
2. **不要断言固定 DPI 值**，改成自校准：`实际 DPI == GetDpiForWindow(窗口)`，再按**读到的那一个 DPI** 算每个 token 的期望值。这样在 100% / 150% / 200% 的任何机器上都是真话。
3. **留一条负向守卫**：断言本进程确实是 Per-Monitor V2，谁把配置或初始化删了，这条立刻红。
4. 产品侧取 DPI 一律用 **`GetDpiForWindow`**，不要用 `GetDpiForSystem` / `GetDeviceCaps`：多显示器下窗口被拖到另一块屏，只有前者会跟着变。

本仓库的实测背景：这台机器是 **150% 缩放（144 DPI）**；同一个 1200×800 的窗口请求，DPI 感知时量到 1200×800，非感知时被虚拟化成 800×533（正好 2/3）。所以「测出来 DPI=96」本身就是虚拟化的指纹。

## 测试里绝不出现真实数据

- 账户 SID 一律用全 0 尾部的假值（`S-1-5-21-0000000000-0000000000-0000000000-1001`）；
- 路径一律用 `Path.GetTempPath()` 下的临时目录，用完删除；
- 截图、日志、运行产物不进仓库（`.gitignore` 已挡）。
