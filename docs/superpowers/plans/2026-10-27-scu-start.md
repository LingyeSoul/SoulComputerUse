# scu start 与 start_session 实现计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让 agent 能通过 `scu start` 与 MCP `start_session` 请求新建会话，由产品拉起宿主窗口，登录始终由操作者亲手完成；同时让「宿主正在启动/等登录」从 `E_LOCK_HELD` 变为可重试的 `E_NOT_READY`。

**Architecture:** 新增一层 Windows 侧的 `HostProcessLauncher`（路径推导 + 交互会话/提权守卫 + 不继承句柄的进程创建 + 等待锁出现），CLI 与 MCP 都只是它的调用者。MCP 适配器从「启动时绑定一个会话客户端」改为「每个工具调用按需解析会话」，因此没有会话时进程也能活着并响应 `start_session`。发现层新增第三个只读观测（所有权记录显示存活且启动中），把该情形从拒绝改为可重试。

**Tech Stack:** C# 14 / .NET 10（`net10.0-windows`）、Win32 interop（`CreateProcessW`、`IsProcessInJob`、`WTSGetActiveConsoleSessionId`）、MSTest 4、命名管道。

**Spec:** `docs/superpowers/specs/2026-10-27-scu-start-design.md`

## Global Constraints

- 登录一律由操作者完成；不得新增任何凭据字段、自动登录、凭据缓存或代输路径（契约 §7.1）。
- 错误消息只允许固定模板 + 枚举/数值/固定文件名；不得出现绝对路径、账户、SID、机器名、nonce、键入正文（契约 §10）。
- 日志字段只用既有白名单 11 项（契约 §10）。
- 不新增网络监听；仍是本机命名管道。
- 不引入 DI 容器；沿用现有「构造函数注入端口」的写法。
- 不加默认参数值；显式声明全部参数（`.editorconfig`）。
- 每个源文件一个类型；file-scoped namespace；`System.*` using 在前；4 空格缩进；花括号必写。
- 生产构建 `TreatWarningsAsErrors`：任何警告即失败。
- 构建：`dotnet build SoulComputerUse.slnx -c Release`
- 契约测试：`dotnet test tests/SoulComputerUse.ContractTests/SoulComputerUse.ContractTests.csproj -c Release --no-build --no-restore`
- 集成测试只在干净真机跑：`dotnet test tests/SoulComputerUse.IntegrationTests/SoulComputerUse.IntegrationTests.csproj -c Release --no-build --no-restore`
- 集成测试绝不使用生产锁名；一律 `Global\SoulComputerUse-Test-<guid>`。
- 未知枚举值、未知方法名一律显式报错，不猜、不忽略。
- 失败必须显式：不静默降级、不自动重试同一动作、不新增兜底异常处理。

## Review Focus

1. 两个 `start` 同时发生（两个 agent，或 agent 与主人各按一次）：同进程内必须序列化（第二个调用排队后返回 `AlreadyRunning`）；跨进程允许各起一个宿主，由宿主单实例锁仲裁，输的宿主以 `E_LOCK_HELD` 退出，调用方仍返回 `Started`。任何情况下不能出现两个可用会话，也不能让调用方返回 `E_LOCK_HELD` 去杀进程。
2. 宿主在拿到锁之前就退出（策略值被禁、安装目录缺 SessionAgent）：`start` 必须返回 `E_HOST_LAUNCH_FAILED` 并带退出码，不能因「进程创建成功」就报 `ok`。
3. 调用者已提权：必须拒绝并给出「以普通权限运行」的固定消息，不能静默让宿主继承高完整性令牌。
4. MCP 客户端在没有 owner 时调用 `get_status`：必须是带 `isError` 的工具结果且 server 继续活着；不能是进程退出，也不能让 stdout 提前 EOF。
5. 登录等待期重复调用 `status` / `get_status` / `start`：只能是 `E_NOT_READY`（retryable），绝不能是 `E_LOCK_HELD`，也绝不能触发清理、接管或杀进程。

2. `probe.LockExists()` + `await probe.IsOwnerPipeReachableAsync(ct)`
3. 管道可达 → `AlreadyRunning`
4. 锁在且 `probe.IsLiveOwnerStarting()` → 抛 `E_NOT_READY`（复用 Task 2 的固定消息）
5. 锁在 → 抛 `E_LOCK_HELD`（复用 `OwnerSessionResolver` 的固定消息文本，抽成共享常量）
6. `!consoleGuard.IsCurrentProcessOnConsoleSession()` → `E_HOST_LAUNCH_FAILED` + `HostLaunchMessages.NotOnConsoleSession`
7. `elevationGuard.IsCallerElevated()` → `E_HOST_LAUNCH_FAILED` + `HostLaunchMessages.CallerElevated`
8. `HostExecutablePath.Resolve(applicationDirectory)`（`FileNotFoundException` → `E_HOST_LAUNCH_FAILED` + `HostLaunchMessages.HostExecutableMissing`，消息含固定文件名）
9. `starter.Start(path, "--new-session")`（`InvalidOperationException`/`Win32Exception` → `E_HOST_LAUNCH_FAILED` + 对应固定消息）
10. 轮询：`clock.Wait(200ms)`，每次重新 `LockExists()`；超时 30 秒
    - 锁出现 → `Started`
    - `handle.HasExited` → 再探一次管道：可达 → `AlreadyRunning`；否则 `E_HOST_LAUNCH_FAILED` + `HostLaunchMessages.HostExitedBeforeLock`（消息含 `ExitCode`，null 时写 `unknown`）
    - 超时 → `E_HOST_LAUNCH_FAILED` + `HostLaunchMessages.TimedOut`（消息含 30）
11. 所有失败路径都 `handle.Dispose()`；成功路径也 `Dispose`（只关闭句柄，不杀进程）。

`HostLaunchMessages` 每条都是常量模板，`E_HOST_LAUNCH_FAILED` 的消息必须能独立读懂并给出下一步动作。

并发约定（必须照做）：

- **同进程**：`StartAsync` 全程持有 `private readonly SemaphoreSlim _gate = new(1, 1)`，第二个调用排队而不是并发开窗。排队后的第二个调用会看到锁已出现，返回 `AlreadyRunning`。
- **跨进程**：两个调用者可能都在宿主拿锁之前通过探测，于是各起一个宿主；宿主自己是单实例锁的唯一仲裁者，输掉的那个宿主以 `E_LOCK_HELD` 退出，而两个调用者都会看到锁出现并返回 `Started`。这是刻意的：把「谁赢」交给宿主，不在调用方加跨进程锁，也不因此报错。
- 这两个约定要写在 `HostProcessLauncher` 的类型注释里，避免后人把它当缺陷「修」成跨进程文件锁。
